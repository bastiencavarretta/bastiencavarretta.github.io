## 1. Running the site locally, right now

From a terminal **inside this devcontainer** (or on a host machine that has Ruby + Bundler installed and this repo's gems available):

```bash
bundle install          # only needed once, or after Gemfile changes
bundle exec jekyll serve
```

Then open **http://127.0.0.1:4000/bastien/** in a browser. Note the trailing `/bastien/` — that's this site's configured `baseurl` (see `_config.yml`), not a Jekyll default. `http://127.0.0.1:4000/` on its own will 404.

`jekyll serve` does two things at once: it builds the static site into `_site/`, and it starts a tiny local HTTP server that serves that folder. It also watches your files, so most edits (content, layouts, styles) trigger an automatic rebuild — but **not** edits to `_config.yml`, which require you to stop (`Ctrl-C`) and re-run the command. We hit exactly that today when adding a new collection.

If you only want the static files without a live server (e.g., to inspect output or run CI-style checks), use:

```bash
bundle exec jekyll build --baseurl /bastien
```

This writes to `_site/` and exits. `--baseurl /bastien` is redundant here since `_config.yml` already sets it, but harmless.

## 2. The vocabulary, bottom to top

This stack is a tower of four layers. Each one manages the layer below it.

### Ruby

The programming language everything here is written in. Jekyll is a Ruby program; when you run `jekyll build`, you're running Ruby code. You don't need to write Ruby to use this repo, but Liquid templates and `_config.yml` values eventually get consumed by Ruby code that a **gem** provides.

### RubyGems, and a "gem"

**RubyGems** is Ruby's package manager (conceptually: npm for Node, pip for Python). A **gem** is one installable package — a `.gem` file containing code, plus metadata about its own dependencies and version. `jekyll` is a gem. So is every plugin this site uses: `jekyll-feed`, `jekyll-archives-v2`, `al_folio_core`, etc. Installing a gem with `gem install X` puts it somewhere on Ruby's load path so `require "X"` can find it.

`GEM_HOME` is the environment variable that says *where* gems get installed. In this devcontainer it's `/usr/local/bundle` — which is exactly why yesterday's permission bug happened: that directory was root-owned, but you (the `vscode` user) needed to write into it.

### Bundler, `Gemfile`, and `Gemfile.lock`

Plain `gem install` is fine for one gem, but a real project needs many gems, at compatible versions, reproducibly, across machines. **Bundler** is the tool that manages that: it reads a `Gemfile` (which gems, roughly which versions), resolves a consistent set of exact versions for every gem *and every gem those gems depend on*, and writes that exact resolution to `Gemfile.lock`.

- `Gemfile` — human-edited. "I want jekyll, jekyll-feed, al_folio_core 1.0.15, ..."
- `Gemfile.lock` — machine-generated by `bundle install`. The exact, pinned dependency graph that was actually resolved and installed. Commit this file; it's what makes "works on my machine" reproducible on another machine.
- `bundle install` — reads `Gemfile`, resolves/installs everything, writes/updates `Gemfile.lock`.
- `bundle exec <command>` — runs `<command>` using *exactly* the gem versions from `Gemfile.lock`, instead of whatever happens to be globally installed. This is why every command in this repo is prefixed `bundle exec jekyll ...` rather than just `jekyll ...` — it guarantees you get this project's pinned Jekyll and plugin versions, not some other version floating around the system.

### Jekyll

**Jekyll is a static site generator.** You give it: page/post content (Markdown + front matter), templates (Liquid + HTML), and stylesheets (Sass/SCSS). It combines them and writes out a folder of plain `.html`/`.css`/`.js` files — no server-side code, no database, nothing that runs per-request. That output (`_site/` here) is what actually gets deployed; a Jekyll site in production is just static files behind a plain web server (e.g., GitHub Pages).

## 3. "Compiling" a website — why that word is a little wrong

It's a reasonable instinct to reach for "compile" here, because *something* is clearly turning source files into a runnable artifact. But "compilation" usually implies translating one language into a lower-level one that a machine executes directly (C → machine code, TypeScript → JavaScript). Jekyll isn't doing that.

What Jekyll actually does is closer to **templating + assembly**:

- Markdown → HTML (a text-to-text conversion, via a Markdown renderer)
- Liquid tags/variables in your templates get evaluated and substituted with real values (dates, titles, loops over `site.posts`, etc.)
- Sass/SCSS → CSS (this part *is* a real compile step, in the traditional sense)
- Everything gets assembled into a folder tree of final HTML pages, matching your permalink structure

The more accurate verb the Jekyll docs themselves use is **"build"** or **"generate."** You'll see this reflected in the actual subcommands: `jekyll build`, not `jekyll compile`. If you want a one-line mental model: **Jekyll is a build pipeline that turns a folder of content + templates into a folder of static HTML**, the same conceptual category as Hugo, Eleventy, or Gatsby's static export — not the same category as `gcc` or `javac`.

## 4. The build pipeline, step by step

Roughly what happens during `jekyll build`, in order:

1. **Read `_config.yml`.** This is only read once, at process start — this is why config edits need a restart, not just a file-save.
2. **Read everything else**: `_pages/`, `_posts/` (and other collections like `_books`, `_news`), `_data/`, `_layouts/`, `_includes/`, `assets/`. Plugins (gems listed under `plugins:`) hook into this stage too — e.g. `jekyll-archives-v2` scans posts for tags/categories and plans extra pages to generate.
3. **Render each document.** For a post: front matter is parsed, Liquid tags/filters in the content run (`{% include %}`, `{% post_url %}`, `{{ page.title }}`, etc.), then the result is run through the Markdown renderer (`kramdown` here, per `_config.yml`) to produce HTML, then wrapped in its `layout` (which itself may wrap in a parent layout).
4. **Write output** to `_site/`, following each document's `permalink`. This is also where Sass gets compiled to CSS, images get processed (the `Imagemagick:` lines you saw in the logs), and any generator-produced pages (pagination, archives, feeds) get written.
5. **Done.** `_site/` is now a complete, self-contained static website. Nothing in it depends on Ruby, Jekyll, or Bundler anymore — you could `zip` it and host it anywhere.

## 5. `build` vs `serve`, and what `--watch` actually does

- `jekyll build` — run the pipeline once, write `_site/`, exit.
- `jekyll serve` — run the pipeline once, then start a local web server on port 4000 serving `_site/`, **and** implicitly enable `--watch`.
- `--watch` — keep a filesystem watcher running; when a source file changes, re-run the build automatically (this is `listen`, the same gem that printed the "directory is already being watched" warning you saw — it's watching `.claude/skills`, which is a symlink duplicate of `.agents/skills`, harmless).

Crucially, the watcher only reacts to *content* file changes. It does not re-read `_config.yml`. If you change plugins, collections, or any other top-level config key, you must stop the server (`Ctrl-C`, or `pkill -f "jekyll serve"`) and start it again.

## 6. Where things live on disk

| Path | What it is |
| --- | --- |
| `Gemfile` / `Gemfile.lock` | Which gems, which exact versions |
| `_config.yml` | Site-wide settings; read once at startup |
| `_posts/`, `_pages/`, `_books/`, ... | Your content, organized into "collections" |
| `_layouts/`, `_includes/`, `_sass/` | Templates and partials (in this repo, these live in gems like `al_folio_core`, not here — see `AGENTS.md`) |
| `_site/` | Build **output** — generated, disposable, gitignored. Delete it anytime; `jekyll build` regenerates it. |
| `/usr/local/bundle` (this container) | Where Bundler/RubyGems actually installs gem code (`GEM_HOME`) |

## 7. Command cheat sheet

```bash
bundle install                                # install/resolve gems per Gemfile
bundle exec jekyll serve                      # build + serve + watch, at :4000/bastien/
bundle exec jekyll build --baseurl /bastien   # one-shot build to _site/, no server
bundle check                                  # verify installed gems satisfy Gemfile, no install
gem env                                       # show RubyGems config (GEM_HOME, load paths, ...)
bundle show <gem>                             # print the on-disk path of an installed gem
```

## 8. How this maps onto today's bundle-permission bug

Worth closing the loop, since it's a good worked example of this vocabulary:

- `GEM_HOME=/usr/local/bundle` — where gems for this project get installed.
- The base devcontainer image had run `bundle install` as **root** while building the image, so `/usr/local/bundle` ended up root-owned.
- `devcontainer.json` runs everything at *container start* as `remoteUser: vscode`, not root.
- So when `postAttachCommand` ran `bundle install`/`bundle check` as `vscode`, it hit `Permission denied` trying to write into a directory it didn't own — nothing to do with Jekyll or your site content, purely a Unix file-permission mismatch between "who built the image" and "who runs the container."
- Fix: `chown -R vscode:vscode /usr/local/bundle` in `.devcontainer/Dockerfile`, so the gem directory is owned by the same user that will actually use it at runtime.
